# План работ

## Решения, которые уже приняты

| Вопрос | Решение | Почему |
|---|---|---|
| Целевой формат | **GeckoLib** (`.geo.json`, Bedrock-совместимый) | сущность для мода; свободные повороты кубов; per-face UV |
| Стратегия конвертации | **детект ящиков + прямой перенос UV** | анализ показал 100% ящиков и 100% прямоугольных UV |
| Запекание атласа | **не нужно** | один материал, все UV — осевые прямоугольники |
| Вокселизация / OBB | **не нужны** | не-ящиков в модели нет |
| Округление координат | **не делать** | модель не на пиксельной сетке, округление сломает стыки |

Java block/item как цель отпал: там повороты только -45/-22.5/0/22.5/45,
а в модели углы вроде 7.5° и 17.5°.

## Фаза 1 — конвертер Mesh → Cube ✅ ядро готово

Реализовано в [`plugin/geckolib_model_importer.js`](../plugin/geckolib_model_importer.js).
Проверено `tools/verify-conversion.mjs`: 108/108 объектов, форма восстанавливается
с точностью 2.4e-15, ноль граней требуют поворота UV.

Что отличается от первоначального замысла:

- **Ориентация осей выбирается по UV, а не по минимальному повороту.** Изначально
  планировалось брать базис, ближайший к единичному. На практике это промахнулось
  на 20 гранях (cube_36 целиком, cube_93, cube_98) — у сильно повёрнутых кубов
  «наименее повёрнутый» базис не совпадает с исходным. Теперь перебираются все 24
  базиса и берётся первый, где UV не требуют поворота на 90°; близость к единичной
  матрице осталась лишь тай-брейкером.
- **Конвенция UV для граней up/down выведена из данных, а не из выкладок.**
  Мой вывод «из головы» дал неверный знак: на слабо повёрнутых кубах он давал
  80–84% отражённых прямоугольников против 12–20% у боковых граней.
- **Зеркальность не требует отдельной обработки.** UV-прямоугольник собирается как
  «текстурная координата в точке с минимальной геометрической координатой», поэтому
  при отражении сам собой получается перевёрнутый прямоугольник (`x1 > x2`),
  который Blockbench и понимает как зеркало.

### Что осталось непроверенным

Ядро математики протестировано, **склейка с Blockbench — нет**: у меня нет
возможности запустить редактор. Под вопросом:

1. Имена и форма API: `mesh.vertices`, `mesh.faces[].uv`, `new Cube(...)`,
   `Undo.initEdit/finishEdit`, `MenuBar.addAction(action, 'filter')`.
2. Порядок углов Эйлера — плагин определяет его в рантайме, создавая пробный куб
   и читая `probe.mesh.rotation.order`. Если этот путь не сработает, будет `XYZ`.
3. Понимает ли geo.json-экспорт перевёрнутые UV-прямоугольники (отражение).
   Затрагивает ~15% граней модели.

### Алгоритм (как реализовано)

Плагин Blockbench, один JS-файл. Действие в меню *Filter* → «Convert Meshes to Cubes».
Ядро — функция `solveBox(faces)`, не зависящая от Blockbench.

На каждый `Mesh`:

1. Собрать уникальные позиции вершин: 8 для ящика, 4 для плоской панели.
2. **Не** трогая нормали, найти из вершины `p0` тройку взаимно ортогональных рёбер
   и проверить, что все 8 точек воспроизводятся как `p0 + ε₁v₁ + ε₂v₂ + ε₃v₃`.
   Нормали здесь бесполезны: на гранях площадью ~1e-6 векторное произведение
   вырождается в шум (напоролись в Фазе 0). Отсюда `center`, `axes`, `size`.
3. Построить все 24 правосторонних базиса, отсортировать по близости к единичному.
4. Для каждого разложить грани меша по граням куба (строго по граням, не по
   вершинам: один угол принадлежит трём граням и несёт на каждой свои UV) и
   посчитать нарушения — случаи, где текстурная `u` непостоянна вдоль оси `v`
   грани. Взять первый базис с нулём нарушений.
5. Собрать UV-прямоугольник: `x1` = текстурная `u` в точке с минимальной
   геометрической координатой вдоль оси `u` грани, и так далее. Отражение
   получается само собой в виде `x1 > x2`.
6. Создать `Cube`: `from`/`to` = center ± size/2, `origin` = center,
   `rotation` = углы Эйлера из базиса.
7. Грани, которых не было в исходнике (48 штук), скрыть через `texture = null`.

Обёртка: `Undo.initEdit` / `Undo.finishEdit`, в конце `Canvas.updateAll()`.
Исходные меши удаляются только если сконвертировалось всё без ошибок.

**Критерий готовности:** визуально модель до и после неотличима, элементов 108.

## Порядок отладки, если что-то пойдёт не так

Проблемы всплывают именно в этом порядке, проверять по одной:

0. **Blockbench отказывается грузить плагин** → имя файла обязано совпадать
   с `PLUGIN_ID`: `geckolib_model_importer.js` ↔ `'mesh_to_cubes'`. Уже наступали.
1. **Форма правильная, положение нет** → ошибка в `origin`/pivot.
2. **Отдельные кубы вывернуты** → неверный порядок углов Эйлера (шаг 6).
   Плагин определяет его в рантайме; фактически применённый порядок печатается
   в отчёте и в консоли.
3. **Текстура повёрнута на 90°** → неверное назначение осей (шаг 4).
4. **Текстура зеркальна** → сначала проверить знаки в `FACE_DIRS` прогоном
   `tools/verify-conversion.mjs`: здоровая картина — 12–20% отражений по `u`
   и 0% по `v` на всех шести гранях; ~80% у какой-то грани = знак перепутан.
   Если знаки в порядке — см. раздел «Зеркальные детали» ниже.
5. **Мерцание на плоских деталях** → z-fighting панелей толщиной 0.001 px.

## Зеркала и повороты на 180° — решено

**Симптом был:** после конвертации часть текстур ложилась неверно, плотнее
всего в районе головы. Пользователь описал точно: «должно быть −x−y, оказалось
+x+y» — то есть перевёрнуты **обе** оси сразу.

**Это оказалось не зеркало, а поворот текстуры на 180°.** Ошибка была в порядке
критериев при выборе базиса:

- Поворот куба на 180° **не меняет ролей `u` и `v`**, поэтому счётчик нарушений
  (который ловит только поворот на 90°) его не видит: 180°-базис проходит
  проверку наравне с единичным.
- Из равных кандидатов выбирался наименее повёрнутый, то есть 180°-вариант
  систематически проигрывал единичному.
- Разницу приходилось добирать отражением UV — что и выглядело как
  «перевёрнуто по обеим осям».

**Исправление:** критерии выбора базиса теперь идут в порядке
`нарушения → отражения → близость к единичной матрице`. Число отражений
**обязано** стоять раньше близости к единичной матрице.

Результат на модели: отражённых кубов стало **2 вместо 20**, полностью
отражённых не осталось. Форма и отсутствие поворотов UV не пострадали.

  На этом предположении сначала сломался и сам калибратор.
- После сборки расхождение фактической ориентации с задуманной — **0 кубов**.

**Три пробы, оставшиеся в плагине** (все печатают результат в отчёт):

| Функция | Что измеряет |
|---|---|

| `rotationError()` | расхождение фактической ориентации с задуманной, в градусах |

## Фаза 4 — импорт из ZIP (в работе)

**Цель:** одна кнопка, которая берёт `.zip` с моделью и текстурой и выдаёт
готовую GeckoLib-модель из кубов.

```
.zip → распаковка → найти .gltf/.glb и .png
     → создать GeckoLib-проект, загрузить текстуру
     → распарсить glTF → solveBox на каждый примитив → кубы
```

### Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Промежуточный OBJ | **не делать** | glTF уже содержит позиции и UV; круг через OBJ добавляет две точки потери и зависимость от чужого импортёра |
| Точка входа | встроить в диалог создания GeckoLib-модели | по просьбе пользователя; о хрупкости см. ниже |
| Формы glTF | **все три**: внешний `.bin`, base64 внутри, бинарный `.glb` | чтобы не упереться в чужой экспорт |
| Не-кубическая геометрия | **пока отказывать** с внятным сообщением | см. ниже |

### Не-кубические модели — временное ограничение

Сейчас конвертер отказывается, если объект не параллелепипед, и показывает,
сколько объектов не прошло. Это **временное** решение: в перспективе тут должна
появиться вокселизация (Фаза 3) с перегенерацией текстуры, чтобы поддерживать
любую геометрию. Отказ — заглушка, а не окончательный ответ.

### Риск встраивания в чужой диалог

Пользователь выбрал встраивание в родное окно создания GeckoLib-модели вместо
отдельного пункта меню. Это выглядит цельнее, но означает вмешательство в чужой
плагин: любое обновление GeckoLib может сломать интеграцию. Держать эту часть
изолированной и с запасным путём — отдельным действием в меню, если перехват
диалога не удался.

### Проверка glTF без Blockbench

Разбор glTF полностью тестируется в Node: `tools/make-gltf-fixtures.mjs` собирает
из `model/model.obj` все три варианта glTF, а `tools/verify-gltf.mjs` парсит их и
сверяет результат `solveBox` с эталоном из OBJ. Расхождений быть не должно.

### Импорт из ZIP — реализовано

Действие **File → Import → GeckoLib из ZIP (glTF + текстура)**.

Порядок работы:

1. `JSZip` распаковывает архив (он есть в Blockbench штатно).
2. Парсер вынимает геометрию, иерархию узлов, текстуру и анимации.
3. **Вся геометрия проверяется до создания чего-либо.** Если хоть один объект
   не представим кубом — импорт отменяется с перечнем проблемных объектов.
   Полусобранный проект пользователю не достаётся.
4. Создаётся проект `geckolib_model`, **`box_uv` принудительно выключается**.
5. Текстура добавляется из байтов (в экспорте Blockbench она вшита в base64).
6. Строятся кости по иерархии узлов, в них раскладываются кубы.
7. Переносятся анимации.

### Анимации: абсолютные значения против смещений

Главная тонкость. В glTF канал задаёт **абсолютную** позу узла, а Blockbench и
GeckoLib хранят **смещение от позы покоя**. У 88 из 142 узлов модели поза покоя
неединичная, поэтому брать значения как есть нельзя:

- поворот: `Δ = R(t)·R0⁻¹`
- сдвиг: `Δ = (T(t) − T0) × 16`

Проверка на настоящей модели: с учётом позы покоя **31 канал** из 219 имеет
нулевой первый кадр, без учёта — только **4**. Медиана угла тоже ниже.

**Что этот тест НЕ доказывает:** порядок умножения. У `R(t)·R0⁻¹` и `R0⁻¹·R(t)`
углы совпадают, различается ось вращения. Выбран первый вариант по рассуждению:
поза покоя запечена в координаты кубов, кость стоит с нулевым поворотом, значит
её поворот применяется в системе координат родителя. Проверяется только глазами.

### Что известно про анимации модели

14 штук, все с **линейной** интерполяцией (кубических сплайнов нет).
Каналов: 219 поворота, 71 сдвига, 4 масштаба. Анимируются **28 узлов, и все они —
чистые кости без мешей**, что даёт чистое разделение: кости двигаются, кубы висят
на них. Каналы масштаба пропускаются — GeckoLib масштаб костей не анимирует.

### Регресс: калибровка после расчёта (исправлено)

В первой версии импорта из ZIP порядок был нарушен:

```
solveBox(...)          ← считает UV по ЗАПАСНОЙ таблице
newProject(...)
calibrateFaceDirs()    ← измеряет уже потом, поздно
```

В результате импорт воспроизвёл ровно тот баг с поворотом текстуры на 180°,
на который ушло несколько заходов отладки. Путь через меши был цел, потому что
там калибровка идёт до цикла конвертации.

Сложность в том, что калибровка требует **живого проекта**, а проект нельзя
создавать до проверки геометрии. Решение — разнести на три шага:

1. проверить геометрию (признак «ящик / не ящик» от конвенции UV не зависит);
2. создать проект и **измерить** конвенции;
3. и только теперь считать окончательную раскладку UV.

**Правило:** `solveBox` обязан вызываться после `calibrateFaceDirs()`. Всегда.

### Что показал первый живой импорт

Отчёт: 108 кубов, 142 кости, текстура 128×128, 48 скрытых граней, 14 анимаций.

**Калибровка UV опровергла статистику.** Измеренная у Blockbench таблица для
`up`/`down` совпала с исходными геометрическими выкладками, а не с той версией,
которую я подогнал под статистику отражений. Запасная таблица в коде обновлена
на измеренную. Подробности — в [format-notes.md](format-notes.md).

**Анимации создавались с исключением.** `createKeyframe` падал с
`Cannot read properties of null (reading 'setLength')`, при этом 2443 кадра
всё же оседали в проекте. Blockbench при создании кадра обращается к
**выбранной** анимации, а она не выбиралась — отсюда `null`. Кадры записывались,
но часть настроек не применялась, и кубы разъезжались.

Исправления:

1. Анимация выбирается сразу после создания (`anim.select()`, плюс запасной
   путь через `Animation.selected`).
2. Знаки осей поворота костей теперь **измеряются** (`calibrateBoneRotation`),
   а не предполагаются: пробная группа поворачивается по каждой оси, и знак
   берётся из фактического `mesh.rotation`.
3. Порядок умножения кватернионов вынесен в диалог импорта: `R(t)·R0⁻¹` против
   `R0⁻¹·R(t)`. Расчётом его не определить — у обоих одинаковый угол,
   различается ось, — поэтому выбор отдан пользователю.

### Разъезд анимаций: смещение считалось не в том фрейме

**Симптом:** после починки исключения кадры создавались все (2443), анимации
проигрывались, но примерно у половины костей кубы улетали далеко от места.

**Причина.** Поза покоя запечена в мировые координаты кубов, а кости стоят
с нулевым поворотом — значит фрейм кости совпадает с модельным. Смещение же
`Δ = R(t)·R0⁻¹` посчитано в **локальном** фрейме узла. Если у родителя есть
поворот покоя `A0`, в модельном пространстве требуется `A0 · Δ · A0⁻¹`, а
подставлялось голое `Δ`, из-за чего ось вращения оказывалась повёрнутой.

**Почему ровно «50 на 50».** Из 28 анимируемых костей у **13** поворот покоя
родителя единичный (там сопряжение ничего не меняет, и они работали), а у **15**
родитель повёрнут — эти и уезжали. Пользователь описал симптом как «у части
на месте, у части смещены» ещё до того, как причина была найдена.

**Исправление:** парсер копит мировой кватернион покоя по иерархии и кладёт в
каждый узел `parentQuat`; при переносе кадров поворот сопрягается им, а сдвиг
поворачивается в модельный фрейм.

### Сопряжение молча не работало

Прошлая правка (сопряжение поворотом покоя родителя) не дала эффекта из-за
опечатки в связке данных: `parentQuat` лежит на узле иерархии, а в таблицу
позы покоя копировался только `h.rest`. В итоге сопряжение всегда получало
единичный кватернион и не делало ничего — при этом ни ошибки, ни предупреждения.

Проверка после исправления: у **15 из 28** анимируемых костей `parentQuat`
неединичный, то есть сопряжение теперь действительно применяется.

**Урок:** правку, которая «должна была помочь», надо проверять не глазами
пользователя, а измерением — доехали ли данные до места применения.

### Поза покоя после импорта

`anim.select()` оставляет последнюю анимацию выбранной, и Blockbench показывает
позу **из неё**, а не позу покоя. Внешне это неотличимо от того, что кубы
собрались не на своих местах. После переноса анимаций выделение снимается,
время сбрасывается на 0 и режим переключается на редактирование.

### Каналы сдвига: улика по величинам

**Наблюдение пользователя:** идеально работают только `flying`, `flying(elytra)`
и `Swim`; у `post` уехали ровно глаза (кости `ad1`, `ad2`).

Разбор по костям (`tools/` + разовые прогоны) показал границу:

| | канал сдвига | поза покоя кости | итог |
|---|---|---|---|
| flying, Swim | только на корневой `bone` | ≈ 0 | ✅ работают |
| post | `ad1`, `ad2`, `A1`, `A2` | 4.2–4.5 px | глаза уехали на ~4 px |
| Idle, sit, walking… | `Head`, `LeftArm`, `RightArm`, `bone5`, `Body` | 20–25 px | улетают далеко |

**Величина промаха совпадает с позой покоя кости**, а не с величиной смещения
(смещения как раз крошечные, 0.2–2 px). У корневой кости поза покоя ≈ 0, поэтому
абсолютное значение и смещение совпадают — отсюда и «эти три работают».

Вывод: канал позиции ведёт себя так, будто применяется **абсолютное** значение,
а не смещение от позы покоя. При этом код вычитает позу покоя, а повороты,
считающиеся по той же схеме и из того же объекта, работают верно — так что
простое «забыл вычесть» отпадает.

**Ложный след, которого удалось избежать.** Сначала корреляция выглядела как
«ломаются анимации с бо́льшим числом каналов сдвига», и напрашивалось выбросить
их как малозначимые. Но проверка величин показала обратное: самые крупные
сдвиги (23.9 px у `flying`, 17.2 у `Swim`) — как раз в работающих анимациях.
Считать «сколько каналов» было бессмысленно, значение имело «на каких костях».

**Текущее состояние:** каналы сдвига по умолчанию не переносятся, отчёт печатает
что именно потеряно. Повороты (1950 кадров из 2443) переносятся и работают.
Осталось выяснить точную семантику канала `position` у костей Blockbench.

### Каналы сдвига подтверждены как источник поломки

После отключения каналов сдвига **все 14 анимаций заработали корректно**.
Диагноз из предыдущего раздела подтверждён: повороты считаются верно
(1950 кадров), ломает именно `position`.

Что известно точно:

- Промах по величине равен **позе покоя кости**, а не величине смещения.
- У корневой кости поза покоя ≈ 0, поэтому она работала при любой трактовке.
- Код вычитает позу покоя; повороты по той же схеме и из того же объекта верны.

Остаётся выяснить точную семантику канала `position` у костей Blockbench.
Пока каналы сдвига выключены по умолчанию, и теряется только подъём корпуса
в `flying` (23.9 px) и `Swim` (17.2 px) плюс мелочь в приседаниях.

### Стартовый экран: три подхода, сработал третий

1. **Своя вёрстка `<li>`** — плитка съезжала влево и была бледнее соседей:
   Blockbench-овские стили держатся на его внутренней разметке.
2. **Клон соседнего пункта** — притащил чужую иконку, а `folder_zip`
   отрисовался обычным текстом поверх названия.
3. **Регистрация `ModelFormat`** ✅ — Blockbench рисует плитку сам, со штатными
   отступами, цветом и подсветкой. Формат нужен только ради плитки, поэтому его

**Урок:** если у хоста есть штатный способ заявить о себе, надо использовать
его, а не воспроизводить оформление руками. Два захода на DOM были потрачены зря.

### Семантика канала `position`: разгадана по величинам

Пользователь заметил, что в `squat`, `squat2`, `squat_attack` голова и руки стоят
чуть позади нужного места. Это ровно те каналы сдвига, что были отключены
(`Head 6.3px`, `LeftArm/RightArm 5.4px`).

Решающими стали три независимых совпадения величины промаха с **позой покоя**
кости (а не с величиной смещения, которое везде мельче 2 px):

| Кость | \|поза покоя\| | Δ | Наблюдалось при включённых сдвигах |
|---|---|---|---|
| `Head` | 25.70 px | 0.23 px | улетала далеко |
| `ad1`, `ad2` (глаза) | 4.24 / 4.50 px | 0.00 / 0.12 px | уехали на ~4 px |
| `Body` | 0.25 px | 0.23 px | не уезжала |
| `bone` (корень) | ≈ 0 | 23.9 px | работала идеально |

Вывод: **канал `position` у кости не прибавляется к позе покоя, а заменяет её
смещение от родителя.** Поэтому запись разности сдвигала кость к родителю на
величину её покоя, а у корня (покой ≈ 0) разность и абсолют совпадали — отсюда
и «работают ровно три анимации».

Режим выбирается в диалоге: `absolute` (по умолчанию), `skip`, `delta`.

### Статичные позы и «пустая» Sleep

Замеры по каждой анимации:

- `post` и `squat` — длина **0 с**, одна временная точка, разброс поворота
  **0.00°**. Это не анимации, а **позы**. Теперь им ставится `loop: 'hold'`
  и длина 0.25 с, иначе они выглядели как анимация в миллисекунду.
- `Sleep` — длина 3 с, но разброс поворота за всё время **0.04°**, при этом
  первый кадр отклоняется от позы покоя на **97°**. То есть это тоже поза,
  просто удерживаемая три секунды: «ничего не происходит» — правильное поведение.

### Дымовой тест: почему он появился

Ошибка `Cannot access 'posMode' before initialization` — обращение к `const` до
объявления — уронила импорт у пользователя. `node --check` такое не ловит:
временная мёртвая зона видна только при исполнении.

Появился `tools/smoke-plugin.mjs`: подменяет объекты Blockbench (`Cube`, `Group`,
`Animation`, `Texture`, `THREE`, `JSZip`, `Dialog`…) и прогоняет **весь** путь
импорта — от нажатия действия до отчёта. Диалог подтверждается сам, JSZip отдаёт
файлы с диска.

Что он проверяет: код исполняется без исключений, кадры анимаций числовые
и конечные, отчёт не содержит сообщений об ошибке. Чего он НЕ проверяет:
численную правоту — калибровка UV в песочнице выдаёт бессмысленные значения,
потому что геометрия пробного куба синтетическая. За правоту отвечают остальные
три теста.

Заодно перенос анимаций сделан **некритичным**: сбой в нём больше не рушит
импорт, кубы и текстура сохраняются, а в отчёт попадает причина.

### Семантика `position`: опыт опроверг гипотезу

Режим `absolute` подняли кости **ровно на величину их позы покоя** (ноги на 16,
голова на 26 при позе покоя 25.70). Это однозначно означает: Blockbench
**прибавляет** значение канала к позе покоя, а не заменяет её. То есть писать
надо смещение — режим `delta`.

Гипотеза «канал заменяет смещение» была построена на том, что промах совпадал
с позой покоя. Совпадение действительно было, но объяснялось иначе: при
включённом `delta` сопряжение поворотом покоя родителя **молча не работало**
(потерянный `parentQuat`, см. выше), и смещения уходили в неверном направлении.

**Ключевой недосмотр:** починив `parentQuat`, я в том же заходе выключил каналы
сдвига по умолчанию — и режим `delta` с работающим сопряжением так ни разу
и не был проверен. Гипотезу строил на данных заведомо сломанной версии.

**Урок:** после исправления нельзя менять вторую переменную в том же заходе.
Иначе неизвестно, что именно проверено, а что нет.

Теперь по умолчанию `delta`, а в отчёт добавлено `кадров с сопряжением: N` —
чтобы факт работы сопряжения был виден, а не предполагался.

### Сдвиги и повороты требуют РАЗНЫХ фреймов

Режим `delta` с сопряжением дал чёткое расслоение:

| Кости | Поворот покоя родителя | Результат |
|---|---|---|
| `Head`, `LeftArm`, `RightArm`, `bone5` | единичный (сопряжение — тождество) | ✅ встали верно |
| `Body`, `bone2`, `bone14`, `bone3`, `bone15` | повёрнут | ❌ уехали вперёд и вниз |

Вывод: **для каналов сдвига сопряжение лишнее.** При этом для поворотов оно
необходимо — это подтверждено заходом с отключёнными сдвигами, где все 14
анимаций работали, включая ветви с повёрнутыми предками.

Асимметрия неожиданная, но подтверждена с обеих сторон: поворот кости
задаётся в модельном фрейме, а сдвиг — в локальном фрейме узла.

Режимы в диалоге: `local` (по умолчанию), `model`, `skip`, `absolute`.

**Про счётчик в отчёте.** Строка «сопряжений применено» считает теперь только
фактически выполненные сопряжения. Первая версия считала кадры, где сопряжение
*могло бы* примениться, — то есть повторяла бы ту же ошибку, из-за которой
молча простаивавшее сопряжение однажды приняли за работающее.

### Хватит гадать: проба фрейма сдвига

Смена режима `model` → `local` не изменила картину, а у `Body` собственный сдвиг
всего **0.23 px** — он физически не может увести кость заметно вперёд. Значит
причина не в том, какой фрейм выбран, и очередная гипотеза была бы пятой подряд.

Добавлена `probeBonePositionFrame()`: кости с повёрнутым родителем ставится
пробный сдвиг по каждой оси, кадр проигрывается, и по фактическому смещению
собирается матрица `M`, для которой `реальное смещение = M · записанное значение`.
Дальше её достаточно обратить.

Важная деталь: нулевая матрица означает, что **превью не пересчиталось**, а не
что кость никуда не поехала. Эти случаи различаются в отчёте — иначе пустое
измерение выглядело бы как содержательный вывод, а такую ошибку мы уже делали
со счётчиком сопряжений.

### Кто на самом деле тащит Body

Скриншот показал, что кадр позиции у `Body` равен нулю (`Z = −1.4e−8`), а модель
при этом разъехалась. Значит `Body` смещает не его собственный сдвиг.

Разбор цепочки: `node_141 → bone → bone5 → Body`, и родитель `bone5` имеет
**позу покоя 20 px** и канал сдвига. Он и тащит всё поддерево.

Заодно объяснилось «ничего не поменялось» при смене `local`/`model`: у всех
костей со сдвигами в `squat_attack` (`Head`, `LeftArm`, `RightArm`, `bone5`,
`Body`) родитель невращённый, поэтому сопряжение для них — тождество, и режимы
дают одинаковые числа. Толкать эту ручку было бессмысленно с самого начала.

### Первая проба измерила не то

Проба выбирала первую попавшуюся кость с повёрнутым родителем и взяла узел-меш
с именем «cube», у которого поза покоя ≈ 0. На такой кости главный вопрос —
сдвигает ли кость сам факт появления кадра — принципиально не виден.

Теперь проба берёт кость с **самой большой позой покоя** (`Head`, 25.7 px) и
меряет три вещи:

1. **Кадр с нулевым значением** — сдвигает ли он кость. Это и есть ответ на
   вопрос «прибавляется или заменяет».
2. Отклик по каждой оси (матрица фрейма), уже за вычетом этого сдвига.
3. Отдельно различается случай «превью не обновилось» — пустое измерение не
   должно выглядеть как вывод.

### Значения кадров верны — проверено по числам

Скриншот дал точную сверку для `bone5` в `squat_attack`:

```
glTF:        T0 = (0.002, 20.002, -1.355) px
             T(0) = (0.002, 19.002, -3.355) px
             Δ  = (0, -1, -2) px
Blockbench:  кадр позиции (0, -0.999999, -2.000000)
```

Записано ровно то, что нужно: знак верен, величина верна, сопряжение у этой
кости тождественно. Проба на `Head` подтвердила и семантику: кадр с нулевым
значением **не сдвигает** кость, отклик единичный — значение прибавляется
к позе покоя.

То есть и формула, и запись правильные, а модель всё равно разъезжается.

### Чего не хватало всё это время

Все проверки были **поканальные**: верна ли величина, верен ли знак, тот ли
фрейм. Ни одна не сравнивала **конечный результат** — где кость реально
оказалась против того, где она обязана быть.

Добавлена `verifyAnimationPose()`: считает позу по glTF на `t=0` (композиция
TRS по всей цепочке предков) и сравнивает с фактическим
`group.mesh.getWorldPosition()` в Blockbench. Печатает вектор промаха на кость.

По такому вектору сразу читается характер ошибки: перепутанная ось даст промах
в другой координате, неверный знак — удвоенное смещение, лишний множитель —
кратную величину. Это первое измерение, проверяющее результат, а не слагаемые.

Проба фрейма теперь выбирает кость с **повёрнутым** родителем (`bone2`), иначе
она не способна отличить режим `local` от `model` — прошлые две пробы брали
кости с единичным родителем и потому этот вопрос не решали.

### Сверка позы: смотреть надо на глубину, а не на промах

Первая версия сверки печатала промахи только у костей с каналом сдвига. На
модели это оказались `ad1`, `A1`, `A2`, `ad2` — мелкие детали у головы, то есть
листья дерева. Промахи 7–9 px были настоящими, но бесполезными: ошибка предка
тащит за собой всё поддерево, и на листе видно лишь накопленное следствие.

Сверка переделана: обходит **все** анимируемые кости, считает промах каждой,
сортирует **по глубине** и называет ту, где расхождение возникает впервые:

```
  [1] bone: промах 0.00 px
  [2] Head: промах 25.70 px (-0.57, -25.67, 0.91)
  [3] ad1:  промах 28.18 px
  ПЕРВАЯ расходящаяся кость: «Head» на глубине 2
```

Если корень стоит верно, а расхождение начинается на конкретной кости — искать
надо ровно там, а не в общей формуле.

**Урок:** при ошибке в иерархии измерять надо не величину, а место её появления.
Величина на листе складывается из чужих ошибок и ни на что не указывает.

### Сверка позы мерила модель в позе покоя

Сверка выдала стройную картину: у всех костей глубины 2 промах по Y **ровно
нулевой**, смещение целиком в плоскости XZ — подпись поворота вокруг Y.
Пересчёт подтвердил: единый угол −67.45° у всех пяти костей, радиус сохраняется
(3.16→3.17, 2.82→2.82, 1.08→1.07).

Но «фактические» координаты оказались **позами покоя**:

```
LeftArm факт (-3.00, 24.62, -1.00)  = её pivot
Head    факт (-0.62, 25.67, -0.87)  = её pivot
```

То есть замер читал модель до применения анимации. Причина: поза считается
только в режиме анимации, а `Animator.preview()` в режиме редактирования ничего
не пересчитывает. «Промахи» были просто разницей между покоем и целевой позой.

Исправлено: сверка переключается в режим анимации, замеряет и возвращает режим
обратно. Добавлена **самопроверка**: если все кости стоят ровно в своих pivot,
отчёт прямо говорит, что анимация не применилась и промахи ничего не значат.

**Урок, второй раз подряд:** любой замер обязан уметь отличать «измерено» от
«не измерилось». В пробе сдвига я такую защиту поставил, а в сверке позы —
забыл, и получил стройные, убедительные и полностью бессмысленные числа.

### Математика анимаций проверена расчётом

Замер позы внутри Blockbench не удался и в режиме анимации: кости продолжали
читаться в позе покоя. Вместо поиска способа заставить редактор пересчитать позу
математика вынесена в ядро (`boneDeltaRotation`, `boneDeltaPosition`) и
проверяется в Node — `tools/verify-animation.mjs`.

Инструмент собирает позу из наших кадров ровно так, как её соберёт Blockbench
(сдвиг снаружи, поворот вокруг точки привязки, вложенные кости перемножаются),
и сравнивает с истинной позой glTF по **всем 14 анимациям и шести моментам
времени**. Перебираются все комбинации: порядок сборки × режим сдвига × формула
поворота.

Результат — из шестнадцати вариантов ровно один точен:

```
✅ TR model     R(t)·R0⁻¹     0.000 px
   TR local     R(t)·R0⁻¹     0.188 px
❌ TR *         R0⁻¹·R(t)     6.191 px
❌ *  skip      *            23.915 px
```

**Главное следствие:** `local` отличается от `model` максимум на **0.19 px**.
Эта настройка физически не может дать видимой разницы — а я перебирал её
несколько заходов, принимая «ничего не поменялось» за загадку вместо ответа.

Заодно инструмент нашёл ошибку в самом себе: первая версия собирала `R·T`
вместо `T·R` и давала промахи до 30 px. Порядок сборки пришлось сделать
перебираемым параметром, а не зашитым допущением.

**Урок:** прежде чем подбирать параметр на глаз, стоит посчитать, какую разницу
он вообще способен дать. Если 0.19 px — подбирать нечего.

### Последнее непроверенное место: углы в кадрах анимации

Смена режима сдвига ожидаемо ничего не изменила — расчёт показал, что она
и не может: разница 0.19 px. Значения кадров доказано верны, значит расхождение
в том, как Blockbench их применяет.

Осталось ровно одно непроверенное место. Знаки осей поворота мерились на
**статическом** повороте группы (`group.rotation` → `mesh.rotation`), а конвенция
углов **в кадрах анимации** у Bedrock-совместимых форматов отличается от
модельной. Это измерение не делалось ни разу.

Почему не делалось: поза не пересчитывалась, замер всегда возвращал покой.
Причина — вызывался `Animator.preview()`, тогда как кадр применяет
`animator.displayFrame()` у аниматора кости. Теперь вызывается он, и в отчёт
выводится, сколько аниматоров реально применилось.

Добавлена `calibrateAnimRotation()`: ставит кости кадр с поворотом по одной оси,
применяет его и смотрит, куда кость реально повернулась. Знаки берутся
из измерения, а не из статической пробы.

### Возврат к рабочему состоянию: порог на сдвиги

Пользователь напомнил то, что я упустил, увлёкшись поиском общей формулы:
**у нас уже было почти рабочее состояние.** При отключённых сдвигах верно было
всё, кроме головы и рук в приседаниях — им не хватало смещений в 5–6 px.
То есть не хватало конкретных **крупных** сдвигов, а не механизма вообще.

Разбор величин объяснил, почему включение всех сдвигов ломало картину:

| Кость | Δ | Роль |
|---|---|---|
| `Head` | 6.3 px | видно глазом, этого и не хватало |
| `LeftArm`, `RightArm` | 5.4 px | то же |
| `bone5` | 2.2 px | тянет за собой `Body` → торс и хвост |
| `Body` | 0.2 px | тянет за собой поддерево |

Крупные сдвиги — на листьях, мелкие — на костях с большими поддеревьями.
Включая всё разом, мы чинили нужное и одновременно ломали остальное.

Режим `big` (по умолчанию) переносит только каналы с размахом от 3 px. На модели
это ровно **11 каналов из 71**: подъём корпуса в `flying` (23.9) и `Swim` (17.2)
плюс голова и руки во всех трёх приседаниях. Остальные 60 отбрасываются,
максимум потерянного — 2.32 px.

**Урок:** когда состояние «почти работает», надо добавлять недостающее точечно,
а не искать общее решение с нуля. Я ушёл от рабочего состояния и потратил
несколько заходов, хотя разница была в одиннадцати каналах.

### Порог — инструмент поиска, а не решение

Пользователь задал верный вопрос: подгонка числа под эту модель не годится для
плагина, который будут ставить на другие модели. Это так, и порог оставлен
только как **средство локализации**.

Логика: при всех включённых сдвигах модель ломается, при пороге 3 px — почти
верна. Значит виновник среди отброшенных каналов, и его можно найти половинным
делением, понижая порог до тех пор, пока картинка не сломается. После этого
порог убирается, а чинится причина.

Порог сделан настраиваемым числом (по умолчанию 2 px), и в отчёт выводится
список крупнейших отброшенных каналов с величинами — чтобы было по чему
бисектировать.

Уже известно из наблюдений:

- порог 3 px — всё верно, кроме нехватки ~2 px по Z в `squat` (это `bone5`, 2.24 px);
- порог 0 (все каналы) — модель разъезжается.

Значит ломающий канал имеет размах **меньше 2.24 px**. Ближайшие кандидаты:
`sit/bone2` и `sit/bone14` (1.96), `walking/LeftLeg` и `RightLeg` (1.41),
`strike/RightArm` (1.05).

### Состояние: всё работает, но через порог

При пороге 2 px все 14 анимаций проигрываются корректно. Значит ломающие
каналы имеют размах **меньше 2 px**.

Что при этом теряется: из 71 канала сдвига отбрасывается 51, и **28 из них
меняются во времени**, то есть несут настоящее движение. Крупнейшие:
`walking/LeftLeg` и `RightLeg` (1.41 px, 5–6 кадров), `strike/RightArm` (1.05),
`flying(elytra)/bone` (1.00). На глаз это незаметно, но формально это потеря.

**Насколько порог универсален.** Он задан в пикселях Minecraft, а это единая
для всех моделей единица (16 px = 1 блок) — то есть он не так произволен, как
выглядит: «сдвиг мельче двух пикселей» значит одно и то же в любой модели.
Но остаётся эвристикой: у модели с более мелкой анимацией порог съест полезное
движение, а причина поломки никуда не денется.

**Что осталось выяснить.** Почему канал сдвига размахом менее 2 px вообще
способен сломать позу — величина не может дать видимого смещения. Пока это
не выяснено, порог маскирует причину, а не устраняет её.

### Причина найдена: рассинхрон времён кадров

Половинное деление порогом сработало. На пороге 0.5 сломались **только**
`walking` и `run`, хотя новые каналы получили ещё `sit`, `strike` и
`flying(elytra)` — и остались целы. Разбор структуры этих каналов дал ответ:

| Канал | Кадры сдвига | Кадры поворота | Времена совпадают | Сломалось |
|---|---|---|---|---|
| `walking/LeftLeg` | 5 | 3 | нет | **да** |
| `walking/bone3` | 6 | 6 | нет | **да** |
| `run/RightLeg` | 6 | 4 | нет | **да** |
| `sit/bone2` | 1 | 1 | да | нет |
| `strike/LeftArm` | 3 | 3 | да | нет |
| `flying(elytra)/bone` | 39 | поворота нет | — | нет |

**Ломается ровно тогда, когда у кости есть и сдвиг, и поворот, но на разных
временах.** Величина смещения ни при чём — порог был ложным следом, он лишь
случайно отсекал такие каналы вместе с мелкими.

**Починка:** для каждой кости берётся объединение времён её каналов, и оба
канала пересэмплируются на него (`sampleChannel`, кватернионы — по кратчайшей
дуге). Кадры сдвига и поворота всегда стоят синхронно.

Это решение **не зависит от модели**: порог убран из умолчаний, все каналы
переносятся. На нашей модели выравнивание затронуло 30 костей.

**Урок:** «сломалось при добавлении мелких значений» толкало к мысли о величине,
хотя различие было структурным. Помогло сравнение сломавшихся каналов
с несломавшимися по всем признакам сразу, а не подбор порога.

### Гипотеза о рассинхроне времён не подтвердилась

Выравнивание времён кадров позу не починило — при всех включённых каналах модель
ломается по-прежнему. Корреляция «сломались те каналы, где времена расходятся»
оказалась случайной.

**И снова изменены две переменные разом:** вместе с выравниванием был убран порог.
Из-за этого неизвестно даже то, помогло ли выравнивание хоть немного. Ровно эту
ошибку я записал уроком двумя разделами выше — и повторил.

Приведено в порядок:

- умолчания возвращены в **заведомо рабочее** состояние: порог 2 px,
  выравнивание выключено;
- выравнивание вынесено в **отдельный флаг**, чтобы проверять его само по себе,
  не трогая порог.

**Что известно точно:**

| Состояние | Результат |
|---|---|
| сдвиги выключены | работает, но голова и руки в приседаниях не на месте |
| порог 2 px | **работает полностью** |
| порог 0.5 px | ломаются `walking` и `run` |
| все каналы | ломается всё |
| все каналы + выравнивание времён | ломается всё |

Причина по-прежнему не найдена. Известно только, что она срабатывает
на каналах сдвига размахом менее 2 px и не связана ни с величиной смещения,
ни с рассинхроном времён.

### Второе строгое решение: предкомпенсация поворота

Выравнивание времён не помогло — гипотеза отпала. Осталось то, что симулятор
показывал с самого начала, но я прошёл мимо: он перебирает **две схемы сборки**
локальной матрицы кости, `T·R` (сдвиг снаружи) и `R·T` (сдвиг внутри поворота).

Точных вариантов ровно два:

```
✅ TR  model  R(t)·R0⁻¹   0.000 px
✅ RT  rt     R(t)·R0⁻¹   0.000 px
```

`model` под сборкой `T·R` в редакторе не работает. Значит, если Blockbench
складывает `R·T`, единственное точное решение — режим **`rt`**: перед записью
смещение поворачивается назад на поворот той же кости в тот же момент.

Это не эвристика и не подгонка: под своей схемой сборки каждый из двух режимов
точен, а третьего не существует. Заодно объясняется, почему ломались именно ноги
в `walking` и `run`: они поворачиваются на 48°, и сдвиг внутри такого поворота
уезжает сильнее всего, тогда как у слабо повёрнутых костей разница незаметна.

Режим `rt` добавлен в диалог. Умолчание остаётся на пороге 2 px — заведомо
рабочем состоянии.

### Предкомпенсация тоже не сработала — обе схемы сборки исключены

Режим `rt` дал худший результат за всё время. Это содержательный итог: раз
`model` (сборка `T·R`) ближе к правде, а `rt` (сборка `R·T`) заметно хуже,
значит Blockbench не складывает матрицу кости ни одним из этих двух способов —
по крайней мере, не так, как это моделирует симулятор.

Проверена и отвергнута гипотеза о вложенных каналах: расчёт показал, что при
пороге 2 px у `walking` и `run` вложенные пары (`bone→LeftArm`) **уже есть**,
и при этом всё работает.

### Итог: причина не найдена, состояние рабочее

Перебраны и отвергнуты:

| Гипотеза | Как отвергнута |
|---|---|
| величина смещения | 0.2 px не может дать видимого сдвига |
| фрейм сдвига (`local`/`model`) | расчёт: разница 0.19 px |
| формула поворота | расчёт: единственная точная — `R(t)·R0⁻¹` |
| рассинхрон времён кадров | выравнивание не помогло |
| сборка `R·T` + предкомпенсация | стало заметно хуже |
| вложенные каналы сдвига | есть и в рабочем состоянии |

**Рабочая конфигурация:** порог 2 px, выравнивание выключено, режим `model`.
Все 14 анимаций проигрываются корректно; теряются только смещения мельче
двух пикселей.

Что стоит попробовать в следующий раз, на свежую голову:

- Сравнить экспорт `.animation.json` из рабочего и сломанного состояний —
  возможно, разница видна прямо в JSON.
- Проверить на второй модели: если порог там окажется другим, это укажет
  на структурную зависимость, а не на числовую.

### Что нашлось в исходниках Blockbench

`BoneAnimator` в `js/animations/timeline_animators.js`:

```js
displayPosition(arr, multiplier = 1)   bone.position.x += arr[0] * multiplier
displayRotation(...)                   bone.rotation.x += added_rotation.x * multiplier
displayFrame()                         поворот → позиция → масштаб
```

Существенное:

- **Негаций осей в `interpolate` нет.** Инверсия осей есть, но только при
  компиляции в Bedrock-формат, то есть при экспорте, а не при отображении.
- Позиция **прибавляется** к `mesh.position` — подтверждает сборку `T·R`
  и корректность режима `model`.
- **Никакой особой обработки разных времён у каналов нет** — каждый канал
  интерполируется независимо. Это объясняет, почему выравнивание не помогло:
  чинить было нечего.
- Интерполяция выбирается из `getLerp` / `getCatmullromLerp` / `getBezierLerp`.

Последний пункт — новая версия: **сглаженная интерполяция**. В glTF она линейная,
а Blockbench умеет catmullrom и bezier. На редких колеблющихся значениях
сглаживание сильно вылетает за пределы заданных точек, а на плотных плавных —
почти незаметно. Данные ложатся ровно так:

| Канал | Кадры | Значения | Ломает |
|---|---|---|---|
| `walking/LeftLeg` | 5 | +1, 0, −1, 0, +1 | **да** |
| `strike/LeftArm` | 3 | почти постоянные | нет |
| `flying(elytra)/bone` | 39 | плавная синусоида | нет |

Интерполяция теперь задаётся явно (`kf.interpolation = 'linear'`).

### Оценка версий, предложенных со стороны

| Версия | Вердикт |
|---|---|
| смещение пивотов | **отпадает**: пивоты берутся из glTF точно, и при их сдвиге ломались бы прежде всего повороты — а они верны |
| GeckoLib плохо переносит сдвиг дочерних костей | **не применимо здесь**: поломка видна в предпросмотре Blockbench, GeckoLib в отрисовке не участвует |
| дрожание масштаба | **отпадает**: замерено, узлов с неединичным масштабом покоя ровно ноль |
| инверсия оси Z | **маловероятно**: геометрия кубов совпадает с OBJ бит в бит, значит оси согласованы; к тому же у ломающихся каналов смещение по X нулевое |

## ПРИЧИНА НАЙДЕНА: научная нотация в значениях кадров

Пользователь удалил кадры позиции у `LeftLeg`, `RightLeg`, `bone3`, `bone15` —
поза выправилась. Значит виноваты именно эти каналы. Но их значения на скриншоте
(`X: 4.8e-8, Y: 1.000000764, Z: -1.000000072`) точно соответствуют glTF, а сдвиг
в один пиксель физически не может согнуть модель пополам.

Разгадка — в **форме записи**, а не в величине. Blockbench хранит значения кадров
строками и разбирает их как выражения Molang. Число `4.759337146609255e-8`
попадает туда в научной нотации, где `e` — не цифра. Разбор ломается, значение
уходит в мусор, и кость разносит целиком.

Проверка по `walking` при пороге 0.5 дала **полное совпадение**:

| Канал | Значений в научной нотации | Состояние |
|---|---|---|
| `bone` | 0 из 111 | работает |
| `LeftArm` | 0 из 117 | работает |
| `RightArm` | 0 из 117 | работает |
| `LeftLeg` | 7 из 15 | **сломана** |
| `RightLeg` | 8 из 18 | **сломана** |
| `bone3` | 6 из 18 | **сломана** |
| `bone15` | 6 из 18 | **сломана** |

Каждый канал с научной нотацией сломан, каждый без неё — работает. Всего таких
значений по модели **220 из 1479**.

Откуда они берутся: это математический ноль, шум float32 из glTF. Осмысленной
величины в них нет.

**Исправление:** перед записью значения очищаются — всё мельче 1e-4 прижимается
к нулю, остальное округляется до четырёх знаков. После этого научной нотации
не остаётся ни одной (проверено: 220 → 0).

**Почему порог «работал»:** он случайно отсекал каналы с шумовыми компонентами
вместе с мелкими. Величина смещения была ни при чём с самого начала — как и
подсказывал здравый смысл, ведь 0.2 px не может ничего сломать.

**Урок:** я много раз проверял, ВЕРНЫ ли числа, и ни разу — в каком ВИДЕ они
записываются. Значение может быть математически точным и при этом непригодным
для приёмника.

## Вторая модель: масштаб и несколько текстур

`model2(gltf).zip` — выгрузка со Sketchfab (`OpenSceneGraph 3.5.6`):
`Dwarf_King.gltf` + внешний `.bin`, 280 узлов, 107 мешей, **4 материала,
2 текстуры**, анимаций нет.

### Множитель координат больше не зашит

Кубы получались гигантскими (32×96×32 при позиции −970). Причина: множитель ×16
был зашит наглухо, а единица glTF значит у разных экспортёров разное.

```
scale=16:  габарит 538 × 550 × 557 px   ← абсурд
scale=1:   габарит 33.6 × 34.4 × 34.8 px ← норма
```

У Blockbench единица glTF — блок (16 px), у выгрузок со Sketchfab — уже пиксель.

`pickScale()` подбирает множитель так, чтобы наибольший габарит попал
в разумный для Minecraft диапазон (4…256 px), предпочитая 16 при прочих равных:

| Модель | Габарит | Множитель | Итог |
|---|---|---|---|
| model (Blockbench) | 3.01 ед. | ×16 | 48.1 px |
| model2 (Sketchfab) | 34.84 ед. | ×1 | 34.8 px |

В диалоге есть ручной выбор, если автоопределение ошибётся.

### Несколько текстур

Материалы модели ссылаются на разные картинки:

| Материал | Объектов | Текстура |
|---|---|---|
| 0 | 85 | `gltf_embedded_0` 128×128 |
| 1, 2 | 2 | `gltf_embedded_1` 16×16 |
| 3 | 20 | нет |

Теперь парсер запоминает картинку каждого объекта, импорт добавляет **все**
текстуры и назначает кубу его собственную. UV-пространство проекта задаёт
самая используемая текстура; Blockbench сам растягивает UV на текстуры другого
разрешения.

В отчёт добавлено предупреждение: **GeckoLib поддерживает одну текстуру
на модель**, поэтому для экспорта их придётся свести в атлас. Это отдельная
задача (Фаза 5).

Результат по model2: **107/107 ящиков**, размеры кубов от 1 до 32 px.

### Наклон и смещение второй модели: внешний узел сцены

Модель появлялась далеко от центра и наклонённой, хотя поворот у элементов
показывался нулевым. Причина — в структуре выгрузки Sketchfab:

```
Sketchfab_model       поворот 160°, сдвиг (6.33, −3.75, −62.38)   ← постановка в витрине
  root
    GLTF_SceneRootNode  поворот 90° вокруг X                      ← конверсия Z-up → Y-up
      …85 объектов
```

Внешний узел несёт **положение модели в витрине Sketchfab** — произвольный
поворот и сдвиг на 62 единицы. Именно он наклонял модель. Узел ниже, с поворотом
на 90°, — законная конверсия осей, её надо сохранять.

Теперь трансформация **внешнего узла сцены отбрасывается** (`ignoreRootTransform`).
Проверено, что это безопасно: у первой модели корневой узел единичный, так что
на неё правка не влияет. У второй результат заметно лучше — модель подходит
к началу координат, и шесть кубов становятся строго по осям вместо ноля.

### Центрирование сделано необязательным

Сначала центрирование включалось по умолчанию, но проверка показала, что оно
сдвинуло бы **первую** модель на 18.6 px по Z — а она стоит правильно и вытянута
по Z намеренно. Положение модели относительно начала координат может быть
осмысленным, и менять его без спроса нельзя.

Поэтому смещение считается всегда и печатается в отчёте, но применяется только
по галочке «отцентрировать и поставить на землю».

### Ориентация и масштаб: ручки вместо угадывания

**Ориентация.** У выгрузки Sketchfab `GLTF_SceneRootNode` несёт конверсию
Z-up → Y-up (+90° вокруг X). Она нужна, но в какой системе автор делал модель,
из файла не видно — и вторая модель встала лицом вверх.

Определить «верх» по габаритам нельзя: у этой модели ширина 24.9, высота 32.1,
глубина 33.6 — почти куб, и любой доворот даёт похожие числа. Автоматика здесь
угадывала бы, поэтому добавлены **ручные довороты** вокруг X и Y.

Доворот применяется как базовая система координат обхода, поэтому попадает
и в позиции, и в точки привязки костей, и в накопленные повороты покоя —
анимации остаются согласованными.

**Масштаб.** Автоподбор даёт разумный порядок, но «правильный» размер зависит
от замысла автора и из файла не выводится. Добавлено поле **своего множителя**
(0 = не задан), которое перекрывает и авто, и выбор из списка.

**Центрирование.** Пользователь подтвердил расчёт: на первой модели оно сдвигает
модель примерно на 19–20 px вперёд. Поэтому осталось выключенным по умолчанию.

### Ориентация и масштаб определяются автоматически

Пользователь подобрал вручную доворот −90° по X и множитель 0.5. Оба значения
оказались выводимыми из данных.

**Ориентация.** Ручной доворот −90° в точности гасил +90° у `GLTF_SceneRootNode`.
Значит и этот узел — часть служебной обёртки выгрузки, а не структура модели:

```
Sketchfab_model → root → GLTF_SceneRootNode
   постановка       —      конверсия Z-up → Y-up
   в витрине               (лишняя, модель уже Y-up)
```

Цепочка опознаётся по именам узлов и отбрасывается целиком. Спуск идёт по
одиночной цепочке; последний узел обёртки как раз и ветвится на содержимое.

Результат на второй модели: высота стала наибольшим габаритом (33.6 против
24.9 и 32.1), а кубов строго по осям стало **17 вместо 6**.

**Масштаб.** В моделях Minecraft тексель текстуры соответствует пикселю модели,
поэтому множитель выводится из отношения площадей — геометрической и UV:

```
множитель = медиана( sqrt(площадь_UV / площадь_геометрии) ) / 2
```

Деление на 2 — потому что текстуру принято делать вдвое подробнее геометрии.
На обеих моделях отношение оказалось ровно двойным:

| Модель | Плотность | Множитель | Проверка |
|---|---|---|---|
| model 1 | 32.00 | 16 | верный |
| model 2 | 0.995 | 0.5 | верный |

Результат округляется к «круглому» значению и проверяется на вменяемость
габарита (4…256 px); при неудаче — запасной подбор по габариту.

Медиана, а не среднее: она устойчива к вырожденным граням, которых в моделях
хватает.

**Ручной ввод сохранён**: список множителей, своё число и довороты. Автоматика
опирается на соглашения, а они выполняются не всегда.

## Третья модель: атлас из восьми текстур

`model3(gltf).zip` — тоже экспорт Blockbench (4.11.2), но с **восемью
материалами**, у каждого своя текстура: 5×128², 64², 2×32².

Текстуры не работали потому, что UV клались в пространство **одной** самой
ходовой текстуры, а остальные семь на неё не ложились. Разные разрешения
в общем UV-пространстве проекта не уживаются.

**Решение — атлас.** Оно же требуется для экспорта: GeckoLib поддерживает одну
текстуру на модель.

`packAtlas()` раскладывает картинки полкой (по убыванию высоты) в холст со
сторонами — степенями двойки. Для этой модели вышло **512×256** без пересечений
и с запасом. Парсер получил `uvRects`: UV каждого объекта пересчитываются
в координаты его прямоугольника в атласе.

Картинки декодируются асинхронно, поэтому текстура в проекте создаётся сразу,
а содержимое подставляется по готовности — так не пришлось перестраивать весь
импорт вокруг ожидания.

Результат: **96/96 ящиков**, множитель 8 (габарит 49 px), **все 3288 UV лежат
внутри атласа**.

Для единственной текстуры атлас вырождается в неё саму, поэтому первые две
модели работают ровно как раньше — проверено, все тесты зелёные.

### Регрессия от атласа: плотность считалась по размеру проекта

После сведения текстур в атлас размер проекта стал размером атласа (512×256),
а плотность текселей домножалась именно на него. Для одной текстуры это одно
и то же, а для восьми — завышение почти втрое.

Исправлено: `texelScale` принимает функцию размера и берёт размер **своей**
текстуры каждого объекта.

### Масштаб третьей модели: метрики расходятся

Проверены две независимые оценки:

1. **Плотность текселей** — из отношения площадей UV и геометрии.
2. **Доля целых размеров кубов** — модели Blockbench строятся на целых пикселях.

Обе на известных моделях дают ровно вдвое больше правильного и требуют
деления на 2 (то есть текстура вдвое подробнее геометрии — устойчивое
соглашение):

| Модель | Плотность | Целые размеры | Верный |
|---|---|---|---|
| model 1 | 16 | 16 | **16** ✓ |
| model 2 | 0.5 | 0.5 | **0.5** ✓ |
| model 3 | **8** | **16** | ? |

На третьей модели они **расходятся вдвое** — значит для неё одно из допущений
не выполняется: либо текстуры не вдвое подробнее, либо размеры кубов не целые
в её собственном масштабе.

Автоматика не может это разрешить, поэтому в отчёт добавлен список соседних
вариантов с их габаритами: выбор своим множителем стал осознанным.

**Урок:** две метрики, согласные на всех проверенных случаях, всё равно могут
разойтись на новом. Это признак того, что обе опираются на соглашение,
а не на закон.

## Четвёртая модель: слитый меш

`model4(gltf).zip` — выгрузка Sketchfab, и вся модель в ней **один меш**:
1416 вершин, 708 треугольников, один примитив. Плагин честно отказывался:
`solveBox` ожидает один ящик на объект.

708 ÷ 12 = **59 кубов**, склеенных экспортёром в единую поверхность.

### Разбиение на связные части

`splitComponents()` разбивает грани по связности. Путь к рабочему критерию:

| Критерий связности | Частей | Ящиков | Не ящиков |
|---|---|---|---|
| общая вершина | 51 | 43 | 8 |
| общее ребро | 51 | 43 | 8 |
| **честное ребро (ровно 2 треугольника)** | **59** | **59** | **0** |

Первые два склеивали кубы, сомкнувшиеся ребром: у них две общие вершины,
и объект получался с 14 вершинами вместо двух ящиков по 8.

Разгадка — в свойстве замкнутой поверхности: **ребро принадлежит ровно двум
треугольникам**. Там, где два куба сомкнулись, у ребра оказывается четыре
смежных треугольника — по этому признаку они и различаются.

### Проверка на всех моделях

| Модель | Объектов | Частей | Ящиков |
|---|---|---|---|
| model 1 | 108 | 108 | 108 |
| model 2 | 107 | 129 | 129 |
| model 3 | 96 | 96 | 96 |
| model 4 | 1 | **59** | **59** |

Ни одна не потеряла ни одного объекта. Вторая распалась на 129 частей вместо
107 — там тоже были слитые меши, просто они и раньше проходили как ящики
по случайности… нет: они распались на честные части, и все 129 остались ящиками.

## Фаза 7: витрина Sketchfab

Поиск и загрузка моделей прямо из Blockbench — через **официальный Data API**,
а не через выкачивание в обход настроек автора. Такой путь не только законен,
но и устойчив: он не ломается при изменении внутреннего протокола просмотрщика.

### Форматы сверены с живым API, а не с документацией

Swagger-страница не отрендерилась, поэтому запросы делались напрямую:

```
GET /v3/search?type=models&downloadable=true&count=24&q=…      → 200, без токена
GET /v3/models/{uid}/download                                   → 401 без токена
     заголовок: Authorization: Token <token>
```

Поля результата: `uid`, `name`, `isDownloadable`, `user.displayName`,
`license.label`, `thumbnails.images[{url,width,height}]`, `archives.gltf.size`,
курсор `next`.

Скачивание отдаёт **временную** ссылку на zip со структурой
`scene.gltf` + `scene.bin` + `textures/` — ровно той, что уже разбирает импорт
(её же имела четвёртая модель). Поэтому вся работа свелась к витрине и токену.

### Что сделано

- `sketchfabSearch()` — поиск, только среди **скачиваемых**: показывать
  остальные значит обманывать ожидания.
- `sketchfabDownload()` — ссылка → архив → распаковка, с отдельными
  сообщениями на каждом шаге и разбором кодов 401/403.
- Витрина: строка поиска, плитки с превью, автором, лицензией и размером
  архива; клик — загрузка и импорт.
- Токен хранится в `localStorage`, задаётся кнопкой «Токен…».
- Диалог настроек импорта вынесен в `askImportOptions()` и переиспользуется:
  скачанная модель проходит тот же путь, что и файл с диска.

### Авторство

Почти все скачиваемые модели идут под лицензией с обязательным указанием
автора, поэтому:

- в плитке всегда видны автор и лицензия;
- после импорта они печатаются в консоль;
- импорт читает `license.txt` из архива и выводит его в отчёт.

Терять эти сведения при конвертации нельзя — это и уважение к автору,
и защита пользователя от нарушения условий.

### Правки витрины по итогам обкатки

**Enter закрывал диалог.** Blockbench трактует Enter как подтверждение окна,
и событие всплывало из поля поиска. Теперь оно гасится (`preventDefault`
и `stopPropagation`) до всплытия, а поиск запускается сам.

**Не было постраничной выдачи.** Показывались только первые 24 результата.
Поле `next` в ответе API содержит готовый URL следующей страницы, поэтому
добавлена плитка «Показать ещё», которая дописывает результаты к уже
показанным. Проверено на живом API: вторая страница даёт ещё 24 записи
без единого повтора с первой.

**Страница формата на стартовом экране была пустой.** Blockbench не знал,
что показать и какой подписью звать действие, — добавлен `format_page`
с описанием и кнопкой «Выбрать архив…».

## Журнал проверенных моделей

Чтобы разбирать поломки на потоке, витрина умеет отмечать модели: ✅ работает,
⚠️ есть проблемы, ❌ не грузится. Отметка ставится по клику на плитке, повторный
клик её снимает.

**Смысл не в самих отметках.** Отметка без данных ничего не объясняет, поэтому
импорт складывает в журнал числа: объектов, не-кубов, текстур, множитель,
анимаций, сколько слитых мешей разделено, предупреждения и итог. Ключ —
`sf:<uid>` модели.

Важные детали устройства:

- Статистика и отметка пишутся **раздельно и не затирают друг друга**: сначала
  импорт кладёт числа, потом пользователь ставит отметку (или наоборот).
- При **отказе** статистика тоже сохраняется — иначе «не грузится» осталось бы
  без объяснения, а это самый интересный случай.
- Клик по кнопке отметки не запускает импорт (`stopPropagation`).

**Сводка** (Help → «Журнал проверенных моделей») сравнивает средние по группам:

```
  признак                  ok   issues     fail
  объектов               59.0      —      0.0
  не-кубов                0.0      —     12.0
  текстур                 1.0      —      7.0
```

Если у всех «не грузится» общий признак — много не-кубов, семь текстур, тот же
множитель — он проявится именно здесь. Плюс список проблемных моделей с
причиной отказа и выгрузка журнала в JSON для подробного разбора.

### Заметки к моделям

Отметка «есть проблемы» без описания через неделю ничего не объясняет, поэтому
к каждой модели можно написать заметку — кнопкой 📝 на плитке.

Для отметок ⚠️ и ❌ окно заметки открывается **сразу после отметки**: это
единственный момент, когда пользователь ещё помнит, что именно поехало.
Отметка при этом уже сохранена, так что отмена окна ничего не теряет.

Заметка хранится отдельным полем и **переживает переотметку** — проверено:
смена статуса `issues → fail` не стирает ни заметку, ни числа импорта.

В сводке заметки выводятся рядом с проблемными моделями, а отдельным блоком
перечисляются те, у кого отметка есть, а заметки нет — по ним причина
неизвестна, и их стоит описать.
